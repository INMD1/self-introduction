> 연구자가 만든 앱을 내부 서버에 배포하고, 관리자가 접근 권한·취약점·로그를 함께 관리하는 플랫폼

> **읽는 기준:** 구현 내용과 보관된 검증 결과를 기준으로 정리했습니다. KPI의 제안값과 주차별 일정은 후속 검증·개선 계획이며, 달성한 성과나 실제 개발 기간을 의미하지 않습니다.

**대상 사용자:** 연구기관의 서비스 개발자, 연구자, 서버 운영자.
**기술 구성:** PHP/Laravel, Livewire, PostgreSQL, Redis, Docker, SSH.
Coolify라는 기존 오픈소스 배포 플랫폼을 기반으로 기관 운영에 필요한 기능을 확장한 프로젝트입니다. 저장소에서는 PADED라는 이름도 사용합니다.

## 1. 문제 정의 (Why)

연구자가 만든 웹 서비스와 AI 앱을 공동 서버에서 운영하면, 앱 실행뿐 아니라 계정 관리·사용자별 권한·취약점 점검·로그 추적을 함께 처리해야 합니다. 이 작업이 분리되어 있으면 배포 담당자의 수작업과 보안 점검 누락 가능성이 커집니다.

- **확인 가능한 문제 규모:** 현재 구현은 감사 기록, 서버 시스템 로그, 컨테이너 로그의 **3개 로그 계열**을 다룹니다. 취약점 점검은 기본적으로 HIGH·CRITICAL의 **2개 심각도**를 우선 확인하도록 설계되어 있습니다.
- **구체적 충돌 지점:** 여러 팀이 서버 1대를 공유하면 다른 팀의 도메인을 차지하거나 호스트 권한을 얻는 설정을 제한해야 합니다. 실제 공유 서버 도메인 정책과 권한 검사 코드가 존재합니다.
- **미확보 수치:** 기존 배포 소요 시간, 보안 누락 건수, 전용 서버 대비 비용은 측정 자료가 없습니다. 따라서 시간·비용 절감률을 확정 성과로 제시하지 않습니다.

## 2. 해결책과 목표 (What)

Git 저장소와 서버를 연결하면 앱을 배포하고, 기관 계정으로 로그인하며, 권한과 로그를 중앙에서 관리하도록 구성합니다.

**현재 확인한 해결책**

- Git 기반 앱 빌드·배포, Docker 이미지·Compose 기반 서비스 실행.
- OIDC: 기관에서 사용하는 계정으로 로그인하는 표준 방식 지원.
- 팀별 리소스 접근 제어와 공유 서버 사용, 공유 서버의 도메인 충돌 방지 정책.
- Trivy: 소스 저장소의 패키지 취약점을 배포 전에 검사. 검사 기능을 켠 경우 검사 실패 시 배포 중단, 발견 시 차단 여부는 설정으로 결정.
- 감사·시스템·컨테이너 로그 수집 및 선택적 Loki 전송, 앱·서버 트래픽 조회.

| KPI | 현재 확인 상태 | 제안 목표 | 측정 방법 |
|---|---|---|---|
| 표준 앱 배포 시간 | 운영 기준값 미측정 | 같은 앱의 수동 배포 대비 중앙값 50% 단축 | 동일 서버·동일 소스로 각 10회 측정 |
| 적용 대상 배포의 취약점 검사 이력 | 검사 코드·저장 기능 존재, 운영 비율 미측정 | 검사 활성화 상태에서 기록률 100% | Git 소스 배포 30회의 배포 ID와 검사 이력 대조 |
| 팀 간 권한 침범 | 권한 검사와 관련 테스트 존재 | 정의한 교차 팀 접근 시나리오의 허용 오류 0건 | 읽기·수정·로그·도메인 접근 회귀 검사 |
| 장애 시 기록 추적 | 로그 수집·전송 기능 존재 | 시범 앱 10개 모두 배포·운영 기록 조회 가능 | 실패 배포와 실행 오류를 재현해 확인 |

위 목표는 제안값입니다. Git 소스를 거치지 않는 배포까지 동일한 패키지 검사가 적용된다고 가정하지 않습니다.

## 3. 범위 및 실행 계획 (How)

### 포함 범위

현재 구현된 앱·서비스 배포, OIDC 로그인, 팀 권한, 공유 서버 정책, 취약점 검사, 로그·트래픽 조회를 대상으로 시범 운영과 검증을 진행합니다. 원본 Coolify 기능과 이 저장소에서 추가한 기관 운영 기능을 구분해 관리합니다.

### 제외 범위

- 컨테이너 격리를 별도 물리 서버 수준의 보안으로 보증하는 일.
- 모든 악성 코드나 실행 중 공격을 탐지하는 기능.
- 기존 Kubernetes 환경 전체 교체와 모든 기관의 인증·규정 충족 인증.
- 배포 속도·보안 사고 감소율을 실측 없이 성과로 확정하는 일.

### 마일스톤 — 후속 계획안

| 기간 | 실행 내용 | 완료 기준 |
|---|---|---|
| 1~2주차 | 시범 앱·사용자 역할·로그 보존 정책 선정, 수동 배포 시간 측정 | 비교 가능한 기준값과 권한 표 확정 |
| 3~4주차 | 자체 이미지로 배포, OIDC·공유 서버·취약점 정책 구성 | 정상 앱 배포 및 차단 사례 재현 |
| 5~6주차 | 로그 전송·트래픽 조회·백업 복구 연결, 교차 팀 접근 점검 | 접근 제한과 기록 추적 시나리오 통과 |
| 7~8주차 | 반복 배포·외부 연결 장애·복구 시험 | KPI 보고서와 운영 절차 확보 |

## 4. 작동 방식 (Work)

**입력 → 배포 전 검사·빌드 → 컨테이너 실행 → 상태와 기록 제공**

1. **데이터 유입:** 사용자가 기관 계정으로 로그인하고 프로젝트, Git 저장소, 환경 변수, 대상 서버를 지정합니다.
2. **시스템 처리:** 작업 큐가 SSH로 대상 서버에 접근합니다. Git 소스 배포에서 설정된 취약점 검사를 수행한 뒤 빌드와 실행을 진행합니다. 검사 미완료 또는 정책상 차단 대상이면 배포를 멈춥니다.
3. **결과 제공:** 사용자는 앱 주소와 배포 상태를 확인합니다. 운영자는 권한이 허용된 범위에서 배포 이력, 취약점 결과, 감사·운영 로그와 트래픽을 조회합니다.

PostgreSQL은 설정·이력을 저장하고, Redis는 비동기 작업을 관리합니다. 화면의 실시간 갱신에는 WebSocket을 사용합니다.

## 5. 리스크 및 기대 효과 (Result)

| 리스크 | 대응 계획 |
|---|---|
| 공동 서버에서 팀 간 리소스나 권한이 섞임 | 팀별 조회 범위·도메인 정책·호스트 권한 제한을 회귀 검사하고, 위험 앱은 별도 서버에 배치 |
| Trivy 이미지나 취약점 DB를 받을 수 없어 배포가 중단됨 | 내부 미러·캐시와 사전 연결 점검을 준비하고, 검사 실패를 정상 통과로 처리하지 않음 |
| Loki 연결 오류 또는 로그 거부로 중앙 기록 누락 | 재시도 대상과 영구 거부를 구분해 감시. 현재 코드에서 일부 4xx는 건너뛰므로 원본 보관·오류 확인 절차 마련 |
| 공식 Coolify 이미지로 교체되어 확장 기능이 사라짐 | 저장소의 자체 이미지 빌드·배포 절차 사용, 변경 전 백업과 복구 시험 |

**기대 효과**

- **정량 목표:** 반복 배포 시간 50% 단축, 적용 대상 검사 이력 100%, 정의한 권한 침범 사례 0건. 실제 비용 절감은 서버 수·운영 시간 측정 후 산정합니다.
- **정성 효과:** 연구자가 서버 운영 절차를 매번 직접 처리하는 부담을 줄이고, 운영자는 서비스 배포와 문제 원인을 한곳에서 확인할 수 있습니다.
- **현재 성과의 경계:** 배포·권한·검사·로그 기능의 구현을 확인했습니다. 운영 사고 감소나 완전한 보안 격리를 입증한 결과는 아닙니다.
