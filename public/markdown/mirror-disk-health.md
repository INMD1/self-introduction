> 미러 서버의 디스크 상태를 자동 수집하고 위험 징후와 사용량을 대시보드로 보여주는 모니터링 도구

> **읽는 기준:** 구현 내용과 보관된 검증 결과를 기준으로 정리했습니다. KPI의 제안값과 주차별 일정은 후속 검증·개선 계획이며, 달성한 성과나 실제 개발 기간을 의미하지 않습니다.

**대상 사용자:** 미러 서버·스토리지 운영자, 인프라 관리자.
**기술 구성:** Python, Bash, smartmontools, Telegraf, InfluxDB, Grafana, systemd.
미러 서버는 파일·패키지의 복제본을 제공하는 서버입니다. SMART는 디스크가 제공하는 건강 상태·오류·수명 등의 자체 진단 정보입니다.

## 1. 문제 정의 (Why)

여러 서버의 디스크를 명령어로 하나씩 점검하면, 온도·불량 섹터·수명 저하가 언제부터 증가했는지 파악하기 어렵습니다. 디스크 종류마다 지표 이름과 의미도 달라 같은 기준으로 우선순위를 정해야 합니다.

- **확인 가능한 수집 주기:** 기본 설정은 SMART **5분**, I/O·파일시스템·소프트웨어 RAID **30초**입니다.
- **정량적으로 설명되는 관측 기회:** 기본 SMART 주기라면 장치당 하루 **288회**의 수집 시점이 생깁니다. 이는 24시간 ÷ 5분으로 계산한 설정상 횟수이며 실제 수집 성공 횟수는 아닙니다.
- **확인 가능한 판정 범위:** ATA HDD/SSD·NVMe·SAS(SCSI)를 공통 지표로 다루고, 상태를 **0 정상·1 경고·2 위험**으로 분류합니다.
- **미확보 손실 수치:** 기존 고장 인지 시간, 장애 건수, 미러 서비스 중단 시간과 복구 비용은 측정 자료가 없습니다.

## 2. 해결책과 목표 (What)

디스크별 진단 정보를 주기적으로 수집해 중앙 시계열 저장소에 모으고, Grafana에서 장치 상태·이력·오류 증가량을 조회하도록 구성합니다.

**현재 확인한 해결책**

- smartctl JSON을 공통 상태·수명·오류 지표와 InfluxDB 저장 형식으로 변환.
- ATA·NVMe·SAS 지표, 셀프테스트, MD RAID·ZFS 상태와 I/O 연계.
- 스핀다운 HDD를 깨우지 않는 조회, RAID 뒤 디스크의 추가 지정.
- 설치·제거 스크립트, 전용 Telegraf 서비스, 접속·데이터 검증용 dhctl.
- Grafana 대시보드와 알림 구성 예시. 대시보드 등록·알림 활성화는 운영자가 별도로 수행합니다.

| KPI | 현재 확인 상태 | 제안 목표 | 측정 방법 |
|---|---|---|---|
| 수집 대상 커버리지 | 자동 탐색·추가 장치 지정 구현, 실제 장치 수 미확인 | SMART 접근 가능한 시범 물리 디스크 100% 등록 | 자산 목록과 장치별 수집 결과 대조 |
| 데이터 신선도 | 설정 주기 5분/30초 | 정상 환경의 SMART 95%가 6분 이내, I/O 95%가 60초 이내 | 수집·저장 시각 차이와 최근 값의 나이 측정 |
| 위험 판정 재현 | 0/1/2 판정과 fixture 테스트 존재 | 정의한 위험 fixture의 위험 누락 0건 | 불량 섹터·NVMe 오류·수명 고갈 등 입력 검증 |
| 수집 중단 인지 | No Data 알림 예시 존재 | 활성화 후 15분 이내 운영자 확인 경로 도달 | 수집기·DB 연결 중단 시험, 알림 시각 기록 |

이 목표는 성공적으로 읽을 수 있는 장치와 정상적인 저장·조회 환경을 전제로 합니다. 수집 주기 5분이 모든 상황에서의 장애 탐지·통지 시간 5분을 뜻하지는 않습니다.

## 3. 범위 및 실행 계획 (How)

### 포함 범위

물리 디스크 SMART 수집, 상태·오류·수명 판정, I/O·파일시스템·MD/ZFS 지표, 중앙 InfluxDB 저장 연계, 대시보드, 설치·검증 도구를 포함합니다. InfluxDB 1.x·2.x 설정 경로를 제공합니다.

### 제외 범위

- 디스크 교체·RAID 복구·데이터 백업의 자동 실행.
- SMART로 정확한 고장 날짜나 모든 장애를 예측하는 기능.
- VM의 가상 디스크에서 물리 디스크 SMART를 직접 얻는 기능.
- 이 저장소만으로 InfluxDB·Grafana 전체를 설치·운영하는 일.
- Grafana 대시보드·알림의 자동 등록과 알림 전달 보장.

### 마일스톤 — 후속 계획안

| 기간 | 실행 내용 | 완료 기준 |
|---|---|---|
| 1~2주차 | 디스크·RAID·DB 목록과 기존 인지 시간 조사 | 접근 가능한 장치 목록·운영 기준값 확정 |
| 3~4주차 | 시범 서버에 수집 구성, RAID 예외 장치 지정 | 대상 장치 100% 등록 및 중앙 데이터 조회 |
| 5~6주차 | 대시보드·알림 설정, 위험·수집 중단 시험 | 판정과 알림 전달 경로 확인 |
| 7~8주차 | 7일 이상 신선도·누락·부하 관찰 | 수집 지연·오류율과 운영 임계값 보고서 |

## 4. 작동 방식 (Work)

**물리 디스크 상태 → 공통 지표·위험 판정 → 중앙 시계열 저장 → 대시보드·설정한 알림**

1. **데이터 유입:** 전용 Telegraf 서비스가 설정된 주기에 Python 수집기를 실행합니다. 수집기는 smartctl로 장치를 찾고 디스크 상태를 읽습니다.
2. **시스템 처리:** 장치별 형식 차이를 공통 필드로 정리하고 오류·온도·수명 임계값에 따라 상태 코드를 계산합니다. Telegraf가 SMART 지표와 I/O 자료를 InfluxDB로 전송합니다.
3. **결과 제공:** Grafana가 호스트·디스크별 상태, 온도, 오류 추이, 수명, I/O를 표시합니다. 운영자가 등록한 알림 규칙에 따라 위험·수집 중단을 알립니다.

예를 들어 NVMe의 미디어 오류가 0보다 크면 현재 판정 규칙상 위험입니다. 수명 사용률은 기본 80% 이상에서 경고, 100% 이상에서 위험으로 분류합니다. 임계값은 실제 장치 특성과 운영 정책에 맞춰 검토해야 합니다.

## 5. 리스크 및 기대 효과 (Result)

| 리스크 | 대응 계획 |
|---|---|
| RAID·USB 경로 때문에 디스크를 읽지 못함 | 장치 타입과 컨트롤러 ID를 확인해 추가 장치 설정, 읽기 실패를 별도 감시 |
| 수집 중단을 디스크 정상으로 오해 | 수집기 자체 지표·마지막 수집 시각·No Data 알림을 함께 확인 |
| SMART 누적 오류를 현재 고장으로 과해석 | 상태 사유와 기간별 증가량·자체 테스트·현장 진단을 함께 판단 |
| 검사나 셀프테스트가 서비스 I/O에 영향 | 스탠바이 건너뛰기를 유지하고 Long 테스트를 비혼잡 시간에 조정, 부하 측정 |
| 중앙 DB 연결 오류로 이력 공백 | Telegraf 오류·버퍼와 네트워크를 점검하고 누락 구간을 기록, 저장 성공률을 별도 측정 |

**기대 효과**

- **정량적으로 가능한 관측:** 기본 주기에서 장치당 하루 288회의 SMART 수집 시점. 실제 저장 성공·장치 응답 여부에 따라 줄어듭니다.
- **후속 정량 목표:** 접근 가능한 장치 커버리지 100%, 정한 신선도 기준 달성, 위험 fixture 누락 0건, 수집 중단 15분 이내 전달.
- **정성 효과:** '지금 정상인가'뿐 아니라 오류·온도·수명이 어떻게 변했는지 확인하여 점검 우선순위를 정하기 쉽습니다.
- **현재 성과의 경계:** 수집·판정·시각화 구성은 확인했지만, 고장 예방률·데이터 손실 감소·금액 절감은 실증하지 않았습니다.
