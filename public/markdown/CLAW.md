> 차량이 이동할 때 Wi-Fi·5G와 유선망 상태가 어떻게 달라지는지 재현하고 기록하는 네트워크 실험 환경

> **읽는 기준:** 구현 내용과 보관된 검증 결과를 기준으로 정리했습니다. KPI의 제안값과 주차별 일정은 후속 검증·개선 계획이며, 달성한 성과나 실제 개발 기간을 의미하지 않습니다.

**대상 사용자:** 네트워크 연구자, 실험 담당자, 통신 시스템 개발자.
**기술 구성:** Python/FastAPI, SQLite, Docker Compose, Containerlab, Open vSwitch, Open5GS·UERANSIM.
테스트베드는 실제 서비스에 영향을 주지 않고 통신 조건을 바꾸어 볼 수 있는 실험 환경입니다.

## 1. 문제 정의 (Why)

이동 중인 차량의 통신 문제를 분석하려면 위치, 무선 신호, 접속 장치 변경, 유선망 지연·손실을 같은 실행 기록으로 연결해야 합니다. 데이터가 따로 남거나 수집 서버 연결이 끊기면 장애 원인을 시간순으로 재구성하기 어렵습니다.

- **확인 가능한 실험 규모:** 유선망, Wi-Fi 차량, 5G 이동, 지역 통합의 **4개 시나리오 패키지**가 있습니다.
- **통합해야 하는 기록:** 위치·무선 신호·접속 변경·핸드오버 시작/완료/실패·유선 RTT·손실·에이전트 상태의 **9개 이벤트 유형**을 공통 형식으로 다룹니다.
- **재현 조건:** 정상·혼잡·장애의 **3개 프로필**을 제공합니다. 장애 프로필에는 중앙 수집 API가 **3회 전송 실패 후 복구**하는 조건이 설정되어 있습니다.
- **미확보 수치:** 기존 실험 준비 시간, 실제 현장에서의 이벤트 유실률과 장애 비용은 미측정입니다. 위 숫자는 구현 범위와 설정값이며 현장 성능값이 아닙니다.

RTT는 데이터가 갔다 돌아오는 시간, 핸드오버는 이동하면서 연결 기지국·공유기를 바꾸는 동작입니다.

## 2. 해결책과 목표 (What)

재현 가능한 시나리오와 공통 이벤트 형식을 제공하고, 전송 전에 데이터를 로컬에 보관하여 중앙 수집 장애에 대비합니다.

**현재 확인한 해결책**

- 시나리오별 실행·종료·기록 방법을 공통 패키지로 제공.
- 모델 기반 데모와 Linux 커널·컨테이너를 사용하는 HIL 실험 경로 제공.
- 전송 전 SQLite에 기록하고, 중앙 서버가 저장·중복 처리 완료를 확인한 항목만 로컬 대기열에서 삭제.
- 실행 ID와 이벤트 ID를 통한 실행 분리·중복 저장 방지.
- 위치·신호·지연·손실을 API와 실시간 스트림으로 조회.

| KPI | 현재 확인 상태 | 제안 목표 | 측정 방법 |
|---|---|---|---|
| 수집 장애 후 이벤트 보존 | 로컬 저장·ACK·재시도 구현 | 정의한 3회 전송 실패 시험에서 유실 0건 | 생성한 고유 ID와 중앙 저장 ID 대조 |
| 재전송으로 인한 중복 | 고유 ID 기반 중복 방지 구현 | 중앙 중복 저장 0건 | 같은 배치를 반복 전송해 고유 건수 확인 |
| 시나리오 재현 | 4개 패키지·3개 데모 프로필 존재 | 3개 프로필을 각각 10회 반복 실행 | 실행 종료 상태와 이벤트 종류 검증 |
| 관측 자료의 출처 구분 | modeled 표기와 실험 경로 구분 존재 | 평가 산출물의 모델/실측 출처 표기 100% | 이벤트·보고서 메타데이터 감사 |

## 3. 범위 및 실행 계획 (How)

### 포함 범위

4개 시나리오의 구성·실행 관리, Wi-Fi·5G 이동성 재현, 유선 품질 조건 제어, 이벤트 수집·조회, 로컬 보관·재전송, 지역 통합 대시보드를 포함합니다. 지역 통합에는 Wi-Fi/5G 조합 **8개**가 정의되어 있습니다.

### 제외 범위

- 실제 도로·이동통신 상용망과 동일한 무선 품질 보증.
- 모델 기반 두 지점 이동 API를 실제 RF 측정으로 해석하는 일.
- 기본 통합 데모의 iperf3 처리량 측정: 설정 필드는 있으나 실행 연결은 아직 미완료.
- ITS-G5 전용 802.11p 무선 장치 구현: 현재는 Wi-Fi/wmediumd 기반 거리 모델 사용.

### 마일스톤 — 후속 계획안

| 기간 | 실행 내용 | 완료 기준 |
|---|---|---|
| 1~2주차 | 이벤트 항목·측정 출처·시나리오 기준값 확정 | 모델과 실제 관측의 판별 기준 확보 |
| 3~4주차 | 3개 프로필 반복 실행, 중단·재전송·중복 검증 | 고유 이벤트 수 대조 보고서 |
| 5~6주차 | 별도 실험 호스트에서 Containerlab·Compose·커널 모듈 연동 | 정상 기동·정리 및 무선 전환 재현 |
| 7~8주차 | 실제 관측과 모델 값 비교, 실행·복구 절차 정리 | 오차와 미지원 항목을 명시한 실험 결과 |

## 4. 작동 방식 (Work)

**차량 경로·통신 조건 → 위치·통신 상태 생성 또는 관측 → 로컬 저장·전송 → 중앙 조회**

1. **데이터 유입:** 연구자가 이동 경로, 속도, Wi-Fi/5G 유형, 지연·손실 조건을 선택합니다.
2. **시스템 처리:** 에이전트가 위치와 통신 상태를 이벤트로 만듭니다. SQLite 대기열에 먼저 기록하고 FastAPI 수집 서버로 묶어서 보냅니다. 응답이 없으면 간격을 늘리며 재시도합니다.
3. **결과 제공:** 중앙 저장소가 이벤트 ID로 중복을 걸러 저장합니다. 연구자는 실행별 이벤트, 이동 기록, 상태 API와 대시보드에서 시간순으로 확인합니다.

모델 데모는 계산한 통신 값을 사용합니다. HIL 경로는 Compose가 컨테이너를 관리하고 Containerlab이 연결선을 구성하며, 커널의 가상 무선 장치와 wmediumd를 사용합니다. 두 경로의 결과는 출처를 구분해 해석해야 합니다.

## 5. 리스크 및 기대 효과 (Result)

| 리스크 | 대응 계획 |
|---|---|
| 모델 값을 현장 측정값으로 오해 | modeled 표기를 유지하고, 결과표에 실행 백엔드·환경·측정 출처를 함께 기록 |
| 장시간 수집 장애로 로컬 디스크 고갈 | 대기열 크기·잔여 공간 감시, 보관 한도와 실험 중지 기준 마련 |
| 커널 모듈·권한·컨테이너 배선 차이로 재현 실패 | 전용 Linux 호스트 사전 점검, wrapper를 통한 기동·정리, 정상 토폴로지로 복원 |
| 서로 다른 실행의 미전송 자료 혼입 | 실행 ID별 대기열 조회·전송 분리를 검증하고 재시작 시험 수행 |

**기대 효과**

- **정량 목표:** 정의한 장애·재전송 시험에서 유실 0건, 중복 저장 0건, 3개 프로필 각 10회 재현.
- **정성 효과:** 차량 위치와 무선·유선 상태를 같은 실행 단위로 비교해 장애 원인 분석과 실험 공유를 쉽게 합니다.
- **현재 성과의 경계:** 재현 시나리오와 내구성 있는 수집 흐름을 구현했습니다. 실제 차량 환경의 통신 품질 향상이나 현장 유실률 0%를 입증한 것은 아닙니다.
