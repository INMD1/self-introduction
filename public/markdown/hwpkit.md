> 한글·Word·웹 문서를 공통 구조로 읽고 다른 형식으로 내보내는 TypeScript 문서 변환 라이브러리

> **읽는 기준:** 구현 내용과 보관된 검증 결과를 기준으로 정리했습니다. KPI의 제안값과 주차별 일정은 후속 검증·개선 계획이며, 달성한 성과나 실제 개발 기간을 의미하지 않습니다.

**대상 사용자:** 문서 처리 서비스 개발자, 사내 업무 자동화 담당자, 문서 데이터 활용 개발자.
**기술 구성:** TypeScript, Node.js·브라우저, JSZip, pako, saxes, tsup, Vitest. DOC 서식 변환에는 선택적으로 로컬 LibreOffice를 연결합니다.
완성형 문서 편집기보다 다른 프로그램에 넣어 사용하는 변환 부품에 가깝습니다.

## 1. 문제 정의 (Why)

한글(HWP/HWPX), Word(DOCX), Markdown·HTML은 문서 저장 방식과 서식 표현이 다릅니다. 형식을 바꿀 때 내용이 남아 있어도 들여쓰기·표·쪽 나눔이 달라져 사람이 다시 수정해야 할 수 있습니다.

**보관 보고서로 확인한 문제와 개선 규모**

| 지표 | 수정 전 | 해당 수정 후 | 측정 조건 |
|---|---:|---:|---|
| 직접 들여쓰기 불일치 | 12,780건 | 400건 | 2026-09-05, 원본 237개·검사 문단 18,434개 |
| 후속 쪽수 오차 합계 | 520쪽 | 178쪽 | 같은 렌더러에서 전후 비교 가능한 236문서 |
| 생성·재읽기 성공 | — | 1,185/1,185건 | 2026-09-08, 실제 원본 237개 × 출력 5형식 |
| 공백 제외 텍스트 완전 일치 | — | 849/1,185건 | 같은 감사의 자체 디코더 결과 비교 |

첫 행의 불일치는 **96.87% 감소**했습니다. 후속 페이지 수정 단계의 직접 들여쓰기 차이는 386건으로 기록되어 있습니다. 서로 다른 단계의 결과이므로 한 실험의 수치처럼 합치지 않습니다.

남은 텍스트 불일치 **336건**에는 목록 표시·제어문자 표현 차이 등이 포함되어 있어 전부 내용 손실이라고 단정할 수 없습니다. 재작업 시간·인건비는 별도로 측정하지 않았습니다.

## 2. 해결책과 목표 (What)

각 형식을 공통 문서 모델인 DocRoot로 읽은 뒤 원하는 형식으로 저장합니다. 사용자는 하나의 API로 여러 변환을 호출하고 경고·실패 결과를 확인할 수 있습니다.

**현재 확인한 해결책**

- HWP·HWPX·DOCX·Markdown·HTML의 5개 기본 입출력 형식과 DOC 입력.
- 기본 5×5, 총 **25개 변환 조합**의 내용 왕복 테스트 정의.
- 문단·글자·표·이미지·구역을 다루는 공통 모델과 구조 조회 API.
- 파일 내용 기반 형식 감지, 지원 한계 경고, 실패 결과 반환과 표 변환 폴백.
- 브라우저 playground와 Node.js용 공개 API. 현재 로컬 package.json 이름은 hwpkit-dev입니다.

| KPI | 확인된 기준값 | 제안 목표 | 측정 방법 |
|---|---|---|---|
| 생성·재읽기 성공 | 보관 감사 1,185/1,185건 | 동일 코퍼스·검사 조건에서 실패 0건 유지 | 입력·번들 해시를 고정해 재감사 |
| 직접 들여쓰기 불일치 | 후속 보관 감사 386건 | 동일 비교기에서 200건 이하 | 문단 대응·단위 허용오차를 고정 |
| 텍스트 완전 일치 | 보관 감사 849/1,185건 | 같은 정의로 900건 이상, 기존 일치 건 회귀 0건 | 방향별 일치 건수와 차이 사유 분류 |
| 기본 내용 보존 | 25개 조합 테스트 존재 | 정의한 25개 조합 모두 통과 | 제목·한글·표 셀 핵심 내용 왕복 검사 |

위 기준값은 보관된 실험 결과이며 소개서 작성 시점의 전체 코퍼스 재실행 결과가 아닙니다. 내부 점수나 재열기 성공을 '문서 정확도 100%'로 표현하지 않습니다.

## 3. 범위 및 실행 계획 (How)

### 포함 범위

5개 기본 형식의 변환·구조 조회, 제한적 DOC 입력, 공통 문서 모델, 손실·오류 안내, 브라우저·Node.js 사용 경로와 회귀 검증을 포함합니다.

### 제외 범위

- PDF 입출력과 DOC 출력.
- 기본 DOC 본문 모드에서 서식·그림·표 구조의 완전 보존. 고급 경로는 외부 LibreOffice 필요.
- 모든 수식·복잡한 차트·개체 배치·글꼴과 모든 한컴 버전의 완전 호환.
- 자체 디코더 왕복만으로 원본 페이지 외관이 동일하다고 인증하는 일.
- 연구 저장소의 자동 패치·LoRA 학습 기능을 라이브러리 자체 기능으로 포함하는 일.

### 마일스톤 — 후속 계획안

| 기간 | 실행 내용 | 완료 기준 |
|---|---|---|
| 1~2주차 | 원본·정답·폰트·렌더러 확보, 방향별 평가 기준 고정 | 재현 가능한 코퍼스와 기준 보고서 |
| 3~4주차 | 남은 들여쓰기·스타일·텍스트 차이를 원인별 분류·수정 | 선택 지표 개선 및 기존 일치 사례 보존 |
| 5~6주차 | 표·이미지·페이지를 독립 프로그램에서 확인 | 라이브러리 재읽기와 외부 열기 결과 분리 |
| 7~8주차 | 전체 코퍼스·25개 조합·공개 API 검증 | KPI와 미지원 범위를 담은 배포 판단 자료 |

## 4. 작동 방식 (Work)

**입력 파일 → 형식별 읽기 → 공통 문서 구조 → 형식별 쓰기 → 결과 파일·경고**

1. **데이터 유입:** 개발자가 파일 바이트나 텍스트를 전달하고 출력 형식을 고릅니다. 명시한 형식이 없으면 파일 내부 구조로 감지합니다.
2. **시스템 처리:** 디코더가 원본을 문단·글자·표·이미지 등 DocRoot로 바꿉니다. 인코더는 단위·서식·문서 구조를 출력 형식에 맞게 기록합니다. 표현할 수 없는 요소는 구현된 폴백·경고 정책으로 처리합니다.
3. **결과 제공:** 성공 여부, 출력 바이트, 경고 목록을 반환합니다. 개발자는 저장·다운로드·후속 처리를 선택하고, inspect로 내부 구조만 확인할 수도 있습니다.

예를 들어 HWP를 DOCX로 바꿀 때 원본을 바로 Word 코드로 치환하는 대신, 공통 구조를 사이에 두어 다른 출력 형식에서도 같은 내용을 재사용합니다.

## 5. 리스크 및 기대 효과 (Result)

| 리스크 | 대응 계획 |
|---|---|
| 파일은 열리지만 서식·페이지가 달라짐 | 텍스트·구조·서식·외관을 별도로 측정하고, 한컴 등 독립 프로그램의 열기·렌더링 결과 확보 |
| 자체 읽기·쓰기의 같은 오류가 왕복 시험에서 가려짐 | 독립 정답 문서·원시 레코드·다른 프로그램 결과와 교차 검증 |
| 특정 문서 개선으로 다른 문서가 나빠짐 | 입력과 평가 조건을 고정해 전수 회귀 검사, 방향별 결과와 악화 문서 목록 공개 |
| 없는 글꼴이나 DOC 외부 도구 때문에 결과가 달라짐 | 글꼴·도구 버전을 기록하고 기본 DOC 모드의 손실을 사전 안내 |

**확인된 결과와 기대 효과**

- **정량 확인 결과:** 2026-09-05 들여쓰기 불일치 12,780→400건, 공통 236문서 쪽수 오차 520→178쪽. 후자의 경우 22문서는 쪽수 오차가 증가해 전체 외관 비회귀 성과로 볼 수 없습니다.
- **후속 정량 목표:** 재읽기 실패 0건 유지, 직접 들여쓰기 불일치 200건 이하, 텍스트 일치 900/1,185건 이상.
- **정성 효과:** 서비스마다 별도 변환기를 만드는 부담을 줄이고, 문서를 다른 업무 시스템이나 웹 서비스에서 활용하기 쉬워집니다.
- **현재 성과의 경계:** 실제 변환·검증 기록이 있지만 완전 무손실·페이지 외관 일치를 보증하지 않습니다. 절감 시간과 금액은 업무 파일럿으로 측정해야 합니다.
