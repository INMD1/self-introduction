> 문서 변환 결과를 정답과 비교하고 AI 수정안을 검증·복원하면서 변환 코드를 개선하는 연구 시스템

> **읽는 기준:** 구현 내용과 보관된 검증 결과를 기준으로 정리했습니다. KPI의 제안값과 주차별 일정은 후속 검증·개선 계획이며, 달성한 성과나 실제 개발 기간을 의미하지 않습니다.

**대상 사용자:** 문서 형식 연구자, 변환 엔진 개발자, AI 기반 코드 개선 연구자.
**기술 구성:** Python, LangGraph, Ollama·LangChain, lxml, PyMuPDF, Node.js/TypeScript runner, 선택적 LibreOffice.
변환기 자체를 제공하는 hwpkit과 달리, 이 프로젝트는 변환 결과의 차이를 분석하고 코드를 고치는 과정을 연구합니다.

## 1. 문제 정의 (Why)

문서 변환 오류는 파일 열기 성공 여부만으로 판단할 수 없습니다. 텍스트·표 구조·서식·정렬이 각각 달라질 수 있고, AI가 총점만 높이는 수정은 다른 내용을 훼손할 수 있습니다. 따라서 수정 전후를 같은 조건에서 비교하고 실패 시 복원해야 합니다.

- **확인 가능한 평가 범위:** HWP·HWPX·DOCX 사이의 **6개 변환 방향**을 정의합니다.
- **회귀 방지 범위:** 텍스트 일치, 요소 재현율, 구조, 서식, 스타일, 정렬의 **6개 보호 지표**를 사용합니다.
- **반복 제한:** 기본 목표 점수는 **0.95**, 반복은 최대 **20회**, 연속 적용·품질 실패는 **3회**에서 중단하도록 구성되어 있습니다.
- **현재 자료 한계:** 소개서 분석 당시에는 원본·정답 코퍼스가 확보되지 않았습니다. 원본·정답 코퍼스를 사용한 현재 모델의 자동 개선률·실행 시간은 새로 측정할 수 없습니다.

0.95는 내부 비교기의 합성 점수입니다. 사람이 보는 외관 정확도 95%를 의미하지 않습니다.

## 2. 해결책과 목표 (What)

변환→비교→검증→원인 추론→소스 수정→재검증을 반복하고, 점수 상승과 보호 지표 비회귀를 함께 만족한 수정만 승인합니다.

**현재 확인한 해결책**

- Node.js runner로 문서를 변환하고 정답 DOCX와 구조·텍스트·서식을 비교.
- 필요한 참조와 도구가 있으면 PDF 위치 비교를 추가.
- Ollama 모델로 차이의 원인과 TypeScript 수정안을 생성.
- runner/src 소스 수정 후 빌드·테스트·실행 번들 동기화.
- 수정 전후 평가 기록을 schema 2로 연결하고 악화·무개선 시 최선 상태 복원.
- 승인된 소스 수정이 있을 때 별도 LoRA 프로젝트에 재학습 신호 전달.

| KPI | 현재 확인 상태 | 제안 목표 | 측정 방법 |
|---|---|---|---|
| 문서별 목표 도달 | 기본 목표 0.95, 현재 코퍼스 결과 없음 | 시범 30문서의 도달률을 기준 모델 대비 10%p 이상 개선 | 같은 입력·정답·가중치·모델 조건 기록 |
| 승인 패치의 품질 비회귀 | 6개 지표 검사 구현 | 정의한 허용오차를 넘는 보호 지표 악화 0건 | 수정 전후 원시 지표와 승인 사유 대조 |
| 잘못된 수정의 복원 | 소스·출력·평가 복원 코드 존재 | 정의한 빌드·무개선·품질 악화 시험 10종 모두 복원 | 파일 해시와 재변환 결과 확인 |
| 승인 기록 추적 | schema 2 전후 연결 구현 | 승인된 패치 100%를 적용·전후 검증에 연결 | diff→rules→patches→apply→verify 이력 감사 |

0.95 도달률의 기준값은 자료 확보 후 측정합니다. 현재 소스의 단일 문서 승인을 전체 코퍼스 비회귀 승인으로 확대 해석하지 않습니다.

## 3. 범위 및 실행 계획 (How)

### 포함 범위

6방향 변환 실행, 정답 비교, 단위·서식 검사, 조건부 PDF 위치 평가, AI 규칙·패치 생성, 연구 runner 소스 수정·빌드·검증·복원, 결과·인계 자료와 학습 신호 생성을 포함합니다.

### 제외 범위

- 검증된 diff를 확인하지 않고 제품 hwpkit/src에 연구 사본 전체를 덮어쓰는 일.
- 원본·정답 문서를 수정해 점수를 올리는 일.
- 모델 자동 수정만으로 모든 문서의 원본 외관·내용을 보장하는 일.
- 참조 PDF·폰트·독립 렌더러 없이 외관 품질을 인증하는 일.
- 별도 LoRA 프로젝트의 실제 모델 학습·배포를 이 저장소 단독 성과로 표현하는 일.

### 마일스톤 — 후속 계획안

| 기간 | 실행 내용 | 완료 기준 |
|---|---|---|
| 1~2주차 | 정답이 있는 30문서와 방향별 평가 과제 확보, 기준 모델 측정 | 입력·정답·가중치·환경을 고정한 기준표 |
| 3~4주차 | LLM 없는 1회 평가로 비교기 신뢰도 확인 | 실패·누락·텍스트·구조 지표의 설명 가능성 확보 |
| 5~6주차 | 제한된 자동 수정 루프, 빌드·회귀·복원 시험 | 승인 궤적 추적과 10종 복원 시험 통과 |
| 7~8주차 | 고정 코퍼스 전체 비회귀·독립 외관 비교 | 목표 도달률과 미해결 오류 보고, 제품 반영 후보 선정 |

## 4. 작동 방식 (Work)

**원본·정답 문서 → 변환·차이 분석 → AI 수정안 → 빌드·재변환·품질 판정 → 승인 또는 복원**

1. **데이터 유입:** 연구자가 원본 문서와 한컴 등에서 만든 정답 DOCX를 준비하고, 필요하면 기준 PDF를 추가합니다. 변환 방향과 모델·목표 점수를 지정합니다.
2. **시스템 처리:** runner가 변환한 결과를 정답과 비교해 차이와 점수를 계산합니다. 목표에 미달하면 AI가 원인을 추론하고 소스를 수정합니다. 빌드·테스트를 거쳐 다시 변환하고 총점과 보호 지표를 확인합니다.
3. **결과 제공:** 점수·차이·수정·승인 사유가 기록됩니다. 개선하지 못하거나 보호 지표가 나빠지면 최선 소스와 산출물로 복원합니다. 승인된 수정은 인계 자료와 LoRA 재학습 신호의 근거가 됩니다.

기록은 verify_i → apply_i → verify_(i+1)로 연결합니다. 즉, 같은 수정의 직전·직후 결과를 연결하여 '실행은 성공했지만 품질은 나빠진 수정'을 구분합니다. LLM을 끄면 1회 변환·평가 후 끝납니다.

## 5. 리스크 및 기대 효과 (Result)

| 리스크 | 대응 계획 |
|---|---|
| AI가 잘못된 파일·범위·단위를 수정 | 소스 경로·검색 일치 조건 확인, 빌드·회귀 테스트, 실패 시 백업 복원 |
| 특정 문서 총점 개선이 다른 문서를 악화 | 현재 보호 지표와 함께 고정 다문서·다방향 전체 평가를 후속 승인 조건으로 추가 |
| 참조 PDF 유무나 가중치 변경이 개선처럼 보임 | 전후 평가 가중치 동일성 확인, 폰트·렌더러·자료 출처 고정 |
| 연구 runner와 실제 라이브러리 소스 차이 | 승인된 diff만 비교·반영하고 양쪽 공개 API·회귀 테스트 별도 실행 |
| 승인되지 않은 수정이 학습 자료로 유입 | schema 2 승인·성공·비롤백 기록으로 신호를 제한하고 LoRA 추출기에서 다시 검사 |

**기대 효과**

- **정량 목표:** 30문서 시범의 목표 도달률 10%p 이상 개선, 승인 패치의 보호 지표 악화 0건, 복원 시험 10종 통과, 승인 이력 추적률 100%.
- **정성 효과:** 오류 발견부터 수정 근거·실험·복원까지 반복 가능한 연구 절차로 남기고, 후속 개발자가 어떤 수정이 도움이 되었는지 확인할 수 있습니다.
- **현재 성과의 경계:** 자동 수정·검증·복원 구조와 품질 계약을 확인했습니다. hwpkit에 보관된 수작업·코드 감사 개선 수치를 AI 자동 개선이나 LoRA 성능으로 귀속하지 않습니다. 소개서 분석 당시에는 이를 입증할 코퍼스·모델 실험 자료가 확보되지 않았습니다.
