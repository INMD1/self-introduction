> 최신 Linux와 브라우저에서 구형 Cisco 서버의 원격 화면·키보드·마우스를 사용할 수 있게 하는 호환성 실행기

> **읽는 기준:** 구현 내용과 보관된 검증 결과를 기준으로 정리했습니다. KPI의 제안값과 주차별 일정은 후속 검증·개선 계획이며, 달성한 성과나 실제 개발 기간을 의미하지 않습니다.

**대상 사용자:** 구형 Cisco UCS 서버 운영자, 데이터센터 관리자.
**기술 구성:** Python, Java 8, Java 에이전트, Docker, Xvfb, x11vnc, noVNC.
KVM은 서버에 모니터·키보드·마우스를 직접 연결한 것처럼 원격으로 조작하는 기능입니다. 이 프로젝트 이름의 KVM은 가상화 엔진을 뜻하지 않습니다.

## 1. 문제 정의 (Why)

구형 Cisco UCS의 원격 콘솔은 오래된 Java·암호화 방식에 의존합니다. 최신 Linux의 Java 실행 정책과 맞지 않으면 서버 자체는 동작해도 원격 화면을 열지 못해 점검·설치·복구가 지연될 수 있습니다.

- **확인 가능한 호환성 조건:** 실행기는 **Java 8**을 선택하고, 해당 실행 프로세스에 구형 TLS·인증서 호환 처리를 적용합니다.
- **확인 가능한 사용 제한:** 웹 버전은 **컨테이너 1개당 세션 1개**, 업로드 **1 MiB 이하**, Java 최대 힙 **512 MiB**로 제한되어 있습니다.
- **장애 원인의 구분:** Java 미탐지, 필요한 JAR 누락, JNLP 세션 만료, 네트워크 접근 실패, TLS·클래스 버전 불일치를 구분해야 합니다.
- **미확보 손실 수치:** 원격 접속 실패 건수, 현장 출동 횟수, 장애 복구 지연 시간은 보관된 실측 자료가 없습니다.

JNLP는 접속 대상과 일회성 인증 정보를 담은 실행 안내 파일이고, JAR는 Java 프로그램 파일입니다.

## 2. 해결책과 목표 (What)

JNLP를 설정 파일로 읽고 Java 뷰어를 직접 실행합니다. 필요한 호환성 조정은 실행 중 메모리에 적용하며 원본 Cisco JAR는 수정하지 않습니다. 웹 버전은 이 실행 환경을 컨테이너에 묶어 브라우저로 화면을 전달합니다.

**현재 확인한 해결책**

- Java 8과 필요한 JAR 폴더 자동 탐색, 환경변수로 명시적 경로 지정.
- 특정 Cisco 클래스의 SHA-256을 확인한 뒤 실행 중 호환성 패치 적용.
- Java Web Start 실행 없이 뷰어 JVM 직접 구동.
- 웹 업로드에서 지원 메인 클래스·JAR·속성만 허용하도록 JNLP 재구성.
- 세션 상태·알려진 오류 요약 표시, 종료 시 프로세스·임시 파일 정리.

| KPI | 현재 확인 상태 | 제안 목표 | 측정 방법 |
|---|---|---|---|
| 지원 조합의 콘솔 접속 | 실행 경로 존재, 장비별 성공률 미집계 | 호환 JAR·장비·네트워크 조합에서 10회 중 10회 화면·입력 확인 | 매번 새 JNLP 사용, 키보드·마우스까지 점검 |
| 접속 준비 시간 | 기존 방식 기준값 미측정 | 동일 조건의 수동 준비 대비 중앙값 50% 단축 | 뷰어 실행 준비부터 화면 표시까지 측정 |
| 원본 JAR 보존 | 메모리 패치 구조 | 원본 JAR 변경 0건 | 실행 전후 파일 해시 대조 |
| 세션 정리 | 정리 코드 존재 | 정의한 종료·오류 시험 후 잔여 프로세스·업로드 파일 0개 | 정상 종료·실행 실패·컨테이너 중지 시험 |

## 3. 범위 및 실행 계획 (How)

### 포함 범위

CLI 실행기, 지원 JNLP 해석, Java·JAR 탐색, 프로세스 범위 호환성 조정, 웹 업로드·원격 화면 전달, 상태·오류 안내와 세션 정리를 포함합니다.

### 제외 범위

- Cisco 서버 펌웨어 자체 수정 및 모든 UCS/JAR 버전 호환 보증.
- 웹 버전의 다중 사용자별 독립 세션과 자체 로그인 기능.
- 현재 네이티브 라이브러리의 ARM 환경 동작 보증. 기본 대상은 Linux x86_64입니다.
- 브라우저의 로컬 ISO를 바로 선택하는 기능. 가상 미디어 창은 컨테이너 파일을 봅니다.
- Cisco 바이너리의 공개 재배포 권한을 이 프로젝트만으로 확보하는 일.

### 마일스톤 — 후속 계획안

| 기간 | 실행 내용 | 완료 기준 |
|---|---|---|
| 1~2주차 | 장비·펌웨어·JAR·Java 조합 및 기존 준비 시간 기록 | 지원 후보 조합표 확보 |
| 3~4주차 | CLI 자동 탐색·새 JNLP·호환성 패치 검증 | 화면 표시와 키보드·마우스 입력 확인 |
| 5~6주차 | Docker 웹 접속·세션 종료·오류 요약 검증 | 단일 세션 정책과 정리 시험 통과 |
| 7~8주차 | 반복 접속·만료·관리망 장애·ISO 마운트 점검 | 지원 범위와 복구 절차 확정 |

## 4. 작동 방식 (Work)

**새 JNLP → Java·JAR 확인 및 메모리 호환 처리 → Cisco 뷰어 실행 → 콘솔 조작**

1. **데이터 유입:** 운영자가 UCS에서 새로 받은 JNLP를 CLI에 지정하거나 웹 화면에 업로드합니다.
2. **시스템 처리:** 실행기는 필요한 Java·JAR·네이티브 라이브러리를 찾고 Java 에이전트를 붙여 뷰어를 실행합니다. 웹 모드에서는 허용한 JNLP 항목으로 실행 문서를 다시 만들고 가상 화면에서 Java 창을 엽니다.
3. **결과 제공:** CLI는 로컬 뷰어와 진단 로그를 제공하고, 웹은 noVNC로 화면과 입력을 전달합니다. 사용 후 종료하면 세션 자원을 정리합니다.

웹의 '실행 중' 표시는 Java 프로세스가 살아 있다는 의미입니다. 실제 서버 연결 성공은 콘솔 화면과 입력 반응으로 확인해야 합니다.

## 5. 리스크 및 기대 효과 (Result)

| 리스크 | 대응 계획 |
|---|---|
| 구형 암호화 호환 설정이 공격 표면을 넓힘 | 지원 장비의 관리망에서 사용하고, 프로세스 범위 적용을 유지하며 장비 교체 계획과 병행 |
| 인증 없는 웹 콘솔에 다른 사용자가 접근 | 기본 loopback 바인딩과 SSH 터널 사용. 원격 공유가 필요하면 별도 인증·접근 제어 적용 |
| 만료된 JNLP로 즉시 종료 | 매 접속 시 새 파일을 받고, 만료·연결 오류를 구분해 안내 |
| 알려지지 않은 JAR로 패치 불일치 | 클래스 해시 검사와 지원 조합표 사용, 실패 시 해당 버전을 별도 검증 |
| 같은 컨테이너의 제어권 공유 | 사용자별 독립 접속이 필요하면 컨테이너를 분리하고 운영자별 사용 시간 관리 |

**기대 효과**

- **정량 목표:** 지원 조합 10회 접속 검증, 준비 시간 50% 단축, 원본 JAR 변경 0건. 교체 비용·현장 출동 절감액은 실측 후 산정합니다.
- **정성 효과:** 구형 서버의 원격 점검·설치를 계속 수행할 수 있고, 호환 환경을 컨테이너로 재현할 수 있습니다.
- **현재 성과의 경계:** 실행·화면 전달·진단 구조를 확인했습니다. 모든 장비에서의 접속 성공이나 서버 수명 연장 기간을 입증한 결과는 아닙니다.
