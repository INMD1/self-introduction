> 네트워크 실험 구성을 그림으로 편집하고 여러 실험 서버를 웹과 데스크톱에서 관리하는 앱

> **읽는 기준:** 구현 내용과 보관된 검증 결과를 기준으로 정리했습니다. KPI의 제안값과 주차별 일정은 후속 검증·개선 계획이며, 달성한 성과나 실제 개발 기간을 의미하지 않습니다.

**대상 사용자:** 네트워크 학습자, 실험망 운영자, 네트워크 개발자.
**기술 구성:** TypeScript/React, Fastify, Electron, Vite, 공통 clab-ui.
폴더 이름은 CLAW_GUI이며, 내부 패키지 이름은 containerlab-app입니다. Containerlab 생태계의 UI와 API를 사용하는 앱입니다.

## 1. 문제 정의 (Why)

Containerlab은 가상 네트워크를 구성하고 실행하는 도구입니다. 명령줄과 YAML 설정에 익숙하지 않은 사용자는 장비·연결선·실행 상태를 동시에 파악하기 어렵고, 여러 실험 서버를 다룰 때 접속 대상과 파일을 혼동할 수 있습니다.

- **구현에서 확인되는 복잡도:** 브라우저와 Electron의 **2개 실행 형태**를 지원하고, 웹·데스크톱 호스트 **2개**와 공통 패키지 **3개**로 구성됩니다. 동일한 편집·로그인·실행 기능을 두 제품에서 유지해야 합니다.
- **다중 서버 문제:** 토폴로지 식별자에 서버 endpoint와 YAML 경로를 함께 사용합니다. 같은 파일명이 다른 서버에 있어도 별도 대상으로 취급하기 위한 구조입니다.
- **미확보 수치:** 초보자의 실습 준비 시간, YAML 작성 오류율, 서버 오선택 횟수에 대한 사용자 실험 결과는 없습니다.

토폴로지는 장비와 연결선을 표현한 네트워크 구성도이고, YAML은 그 구성을 저장하는 텍스트 파일입니다.

## 2. 해결책과 목표 (What)

같은 편집 화면과 중계 서버를 웹·데스크톱에서 재사용하고, 그림 편집·파일 관리·실행 상태·터미널을 연결합니다.

**현재 확인한 해결책**

- 노드·연결선 편집, YAML 코드 편집, 위치·색상 같은 시각 정보 저장.
- 여러 clab-api-server 접속 대상 관리와 인증 세션 처리.
- 랩 배포·삭제 요청, 실행 상태와 인터페이스 통계 수신, 터미널 연결.
- 수정 버전 번호로 오래된 편집 내용의 덮어쓰기 감지.
- 서버 없이 편집을 체험하는 브라우저 샌드박스 모드.

| KPI | 현재 확인 상태 | 제안 목표 | 측정 방법 |
|---|---|---|---|
| 초보자 실습 구성 시간 | 비교 실험 미실시 | 같은 과제의 CLI 방식 대비 중앙값 30% 단축 | 초보자 5명이 두 방식으로 동일 과제 수행 |
| 웹·데스크톱 핵심 흐름 일치 | 공통 런타임·서버 구현 | 정의한 공통 시나리오 10개 모두 통과 | 로그인·저장·배포·삭제·터미널 등 비교 |
| 서버 간 대상 혼동 | 서버별 식별자·세션 분리 구현 | 서버 2대의 동명 파일 시험에서 오대상 작업 0건 | 저장·조회·삭제 요청 목적지 추적 |
| 연결 복구 후 표시 정합성 | 이벤트 스트림·상태 관리 구현 | 정의한 재연결 시험 10회 모두 실제 상태와 일치 | API 응답과 화면 상태 비교 |

## 3. 범위 및 실행 계획 (How)

### 포함 범위

웹·Electron 앱, 공통 편집 화면, 인증·세션, 토폴로지 파일과 시각 정보 관리, 다중 서버 연결, 배포·삭제 요청 중계, 상태 스트림과 터미널을 포함합니다.

### 제외 범위

- 별도 clab-api-server의 설치·운영과 Containerlab/Docker 엔진 자체 개발.
- 일반 CLAW Portal API와 자동으로 호환된다는 보증. 두 저장소는 사용하는 API가 다르므로 별도 연동 검증이 필요합니다.
- 브라우저 샌드박스에서 실제 컨테이너 배포·삭제.
- 모든 장비 이미지의 재배포 권한 확보 및 모든 운영체제 설치 패키지의 서명 완료.

### 마일스톤 — 후속 계획안

| 기간 | 실행 내용 | 완료 기준 |
|---|---|---|
| 1~2주차 | 사용자 과제와 서버 2대 시험 환경 준비 | 과제·역할·비교 시간 기준 확정 |
| 3~4주차 | 편집·파일 저장·다중 서버 동작 검증 | 동명 파일과 수정 충돌 시험 통과 |
| 5~6주차 | 실제 API 서버와 배포·삭제·터미널·재연결 검증 | 요청 목적지와 실제 랩 상태 일치 |
| 7~8주차 | 웹·데스크톱 공통 시험과 초보자 사용성 평가 | 공통 시나리오 결과와 시간 비교 보고서 |

## 4. 작동 방식 (Work)

**그림·YAML 편집 → 공통 중계 서버 → 외부 실험 서버 실행 → 실시간 상태 표시**

1. **데이터 유입:** 사용자가 API 서버에 로그인하고 구성 파일을 열어 장비와 연결선을 편집합니다.
2. **시스템 처리:** React 런타임이 공통 편집 엔진에 명령을 전달합니다. Fastify 중계 서버는 인증 세션과 토폴로지 수정 상태를 관리하고, 파일 저장·실행 요청을 외부 clab-api-server로 보냅니다. 실제 Containerlab·Docker 조작은 외부 API 서버가 수행합니다.
3. **결과 제공:** 외부 서버의 실행 상태·통계를 이벤트 스트림으로 받아 화면을 갱신하고, 필요하면 장비 터미널을 엽니다.

실행에 필요한 장비·링크 정보는 YAML에, 위치·색상 같은 표시 정보는 별도 annotations에 저장합니다. 웹과 데스크톱은 공통 런타임과 서버 코드를 사용합니다.

## 5. 리스크 및 기대 효과 (Result)

| 리스크 | 대응 계획 |
|---|---|
| 외부 API 서버 버전·권한 차이로 기능 실패 | 지원 API 버전·역할별 동작을 정하고 서버 조합별 연동 시험 수행 |
| 서버 A의 파일을 서버 B의 파일로 오인 | endpoint와 경로를 함께 사용하는 식별자를 유지하고 동명 파일 회귀 시험 |
| 동시 편집·재연결 후 덮어쓰기 또는 오래된 상태 표시 | 수정 버전 충돌 감지, 저장 전 재조회, 스트림 복구 후 상태 동기화 검증 |
| 개발용 인증서 설정을 운영에 그대로 사용 | 운영용 인증서와 상위 API TLS 검증 설정을 적용하고 연결 실패를 확인 |

**기대 효과**

- **정량 목표:** 과제 수행 시간 30% 단축, 공통 시나리오 10개 통과, 정의한 다중 서버 시험의 오대상 작업 0건.
- **정성 효과:** 처음 접하는 사람도 네트워크 구조를 그림으로 이해하고, 운영자는 여러 실험 서버를 같은 화면에서 관리할 수 있습니다.
- **현재 성과의 경계:** 웹·데스크톱 공통 구조와 네트워크 편집·실행 연동을 확인했습니다. CLAW 전용 GUI 통합이나 사용자 시간 절감은 아직 실증 결과가 없습니다.
