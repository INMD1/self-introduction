> 검증된 문서 변환 수정 사례로 AI를 추가 학습시키고, 기능 평가를 통과한 모델만 사용하는 연구 파이프라인

> **읽는 기준:** 구현 내용과 보관된 검증 결과를 기준으로 정리했습니다. KPI의 제안값과 주차별 일정은 후속 검증·개선 계획이며, 달성한 성과나 실제 개발 기간을 의미하지 않습니다.

**대상 사용자:** 문서 변환 연구자, AI 모델 개발자, 학습 데이터 품질 담당자.
**기술 구성:** Python, Unsloth, Transformers·TRL, LoRA/rsLoRA, ChromaDB, Ollama, GGUF.
LoRA는 큰 AI 모델 전체를 다시 학습하는 대신 일부 추가 가중치를 학습하는 방법입니다. 이 프로젝트는 변환 라이브러리와 별도의 연구 프로젝트입니다.

## 1. 문제 정의 (Why)

일반적인 코드 AI는 HWP·HWPX·DOCX의 세부 저장 규칙을 충분히 알지 못할 수 있습니다. 검증되지 않은 수정 답변을 학습하면 오류를 정답으로 익히고, 같은 문서가 학습·평가 양쪽에 들어가면 성능이 실제보다 높아 보일 수 있습니다.

- **확인 가능한 대상 범위:** HWP·HWPX·DOCX 사이의 **6개 변환 방향**을 다룹니다.
- **데이터 승인 조건:** 점수 기반 수정 사례는 schema **2**의 적용 기록, 수정 전후 검증, 성공·비롤백·핵심 지표 비회귀를 요구합니다. 이전 형식의 총점만 있는 로그는 자동 정답에서 제외합니다.
- **학습 최소 조건:** DPO에 사용할 선호쌍이 **8개 미만**이면 DPO를 건너뛰는 경로가 있습니다. 기본 LoRA 설정은 rank **32**입니다. 이는 학습 설정이며 성능 수치가 아닙니다.
- **현재 자료 한계:** 소개서 분석 당시에는 학습 데이터·모델 산출물·연결 연구 코퍼스가 확보되지 않았습니다. README의 청크 수나 모델 품질 주장을 현재 데이터·성능으로 재확인할 수 없습니다.

SFT는 정답 예제를 따라 배우는 학습이고, DPO는 좋은 답과 나쁜 답의 비교로 선호를 학습하는 방식입니다.

## 2. 해결책과 목표 (What)

공식 명세와 검증된 패치 이력을 추적 가능한 학습 자료로 만들고, 학습·평가 자료를 문서 단위로 분리합니다. 학습 후에는 실제 코드 적용·빌드·재변환을 평가해 기존 모델과 비교합니다.

**현재 확인한 해결책**

- 공식 명세 추출 시 원본 파일명·SHA-256 기록, 명세 검색용 RAG 구성.
- 승인된 연구 궤적에서 진단·패치·전체 과정·점수 변화 자료 추출.
- FILE/SEARCH/REPLACE 또는 NO_EDITS라는 공통 응답 계약 적용.
- 중복 제거와 원본문서 기준 학습·평가 분리.
- 정답 코드가 길이 제한으로 잘리는지 검사하고, strict 패치 정답 절단 시 학습 중단.
- SFT·선택적 DPO·GGUF 내보내기·Ollama 후보 모델 생성.
- 동일한 평가 집합에서 기존 모델 대비 기능 지표 회귀 검사 후 후보 승격.

RAG는 답변 전에 관련 명세를 찾아 모델에 제공하는 방식이며, 검색 자료가 모두 검증된 학습 정답이라는 뜻은 아닙니다.

| KPI | 현재 확인 상태 | 제안 목표 | 측정 방법 |
|---|---|---|---|
| 승인 패치의 근거 추적 | 검증 필터·원본 메타데이터 구현, 현재 학습셋 없음 | 승인된 점수 기반 패치의 궤적 추적률 100% | 데이터별 apply·전후 verify 연결 확인 |
| 문서 단위 데이터 누수 | 분리·겹침 검사 구현 | train/eval/최종 평가 간 원본문서 중복 0건 | 방향·변형을 같은 원본 ID로 정규화해 교집합 확인 |
| strict 패치 정답 절단 | 학습 전 검사·중단 구현 | 절단된 strict 패치 정답 0건 | 실제 토크나이저 길이 검사 |
| 기능적 개선 | 후보 평가 코드 존재, 모델 실측값 없음 | 독립 60과제에서 기존 모델 대비 개선 성공률 10%p 이상 상승 | 6방향 각 10과제, 같은 입력·분모·평가 환경 비교 |

기능 목표에는 텍스트·구조 악화 방지 조건을 추가하는 후속 작업이 필요합니다. 현재 end2end 평가는 주로 총점 상승을 보므로, 연구 저장소의 보호 지표 승인과 동일하다고 간주하지 않습니다.

## 3. 범위 및 실행 계획 (How)

### 포함 범위

명세 추출·검색, 승인 궤적 기반 데이터 생성, 데이터 품질 감사, SFT·DPO 학습 경로, 모델 내보내기, 격리된 기능 평가와 후보 승격 절차를 포함합니다.

### 제외 범위

- 현재 모델 성능 상승·6방향 정확도·학습 시간·VRAM 사용량을 실증 성과로 확정하는 일.
- 검증되지 않은 AI 답변·구형 총점 로그를 자동 정답으로 사용하는 일.
- 모든 합성·수동 자료가 자동으로 사실 검증되었다는 보증.
- GPU·모델 다운로드·충분한 원본 코퍼스 없이 학습 완료를 보장하는 일.
- 라이브러리의 실제 사용자 문서를 자동으로 수집하는 기능.

### 마일스톤 — 후속 계획안

| 기간 | 실행 내용 | 완료 기준 |
|---|---|---|
| 1~2주차 | 공식 명세·검증 궤적 확보, 60개 독립 평가 과제 설계 | 원본 추적·사용 범위·분리 기준 확정 |
| 3~4주차 | 데이터 생성·중복·누수·정답 절단 감사 | 추적률 100%, 누수·strict 절단 0건 |
| 5~6주차 | GPU 환경에서 소규모 SFT, 충분한 선호쌍이 있으면 DPO | 버전·설정·손실·자원 사용량 기록 |
| 7~8주차 | 동일 과제의 기존·후보 모델 비교, 보호 지표 게이트 보강 | 기능 개선·비회귀를 확인한 후보만 승격 |

## 4. 작동 방식 (Work)

**공식 명세·승인된 수정 궤적 → 정제·분리 → 추가 학습 → 실제 수정 평가 → 후보 모델 승격**

1. **데이터 유입:** 명세 문서와 hwpkit_research의 diff·규칙·패치·전후 검증 기록을 읽습니다. 승인되지 않은 수정은 점수 기반 정답에서 제외합니다.
2. **시스템 처리:** 공통 응답 형식으로 자료를 만들고 중복·문서 누수·길이 절단을 검사합니다. LoRA 학습과 필요한 DPO를 거쳐 GGUF를 만들고, 기존 모델과 후보 모델을 같은 평가 집합에서 비교합니다.
3. **결과 제공:** 학습용 JSONL·통계·모델 파일·기능 평가 보고서가 생성됩니다. 재학습 스크립트는 회귀 검사 통과 시 배포용 모델 이름으로 복사하고, 실패하면 후보를 제거하고 재학습 신호를 남깁니다.

기능 평가는 응답 해석, 수정 대상 일치, 격리된 코드 적용·빌드, 재변환 점수 개선을 나누어 봅니다. 문법이 맞는 코드와 실제 변환이 좋아지는 코드는 별도의 기준입니다.

## 5. 리스크 및 기대 효과 (Result)

| 리스크 | 대응 계획 |
|---|---|
| 오류·환각·검증 안 된 예제를 학습 | 승인 궤적 필터 유지, 공식 근거와 생성 진단을 구분하고 수동 자료도 감사 |
| 같은 문서의 역방향·변형이 평가에 섞임 | 원본 ID 단위 분리, 새 자료 추가 시 겹침 재검사 |
| 긴 입력으로 정답 패치가 잘림 | 학습 전 실제 토큰 길이 검사, 입력 축약·문맥 길이 조정 후 재감사 |
| 총점은 오르지만 텍스트·구조가 나빠짐 | 기능 승격에도 핵심 지표 하한·비회귀 조건과 고정 다문서 평가 추가 |
| GPU 메모리·Python/CUDA 의존성 문제 | 지원 버전 환경을 고정하고 작은 모델·배치로 사전 시험, 자원 사용량 기록 |

**기대 효과**

- **정량 목표:** 승인 궤적 추적률 100%, 문서 누수 0건, strict 패치 정답 절단 0건, 독립 평가의 기능 개선 성공률 10%p 이상 향상.
- **정성 효과:** 문서 변환 분야의 수정 경험을 반복 활용하고, 학습·모델 교체의 판단 근거를 남길 수 있습니다.
- **현재 성과의 경계:** 데이터 품질 통제와 학습·평가 코드가 있습니다. 학습 완료나 모델의 변환 품질 개선을 입증하는 실험 결과는 아직 없습니다. 9,142청크 등 README의 수량은 현존 파일로 재확인하지 못해 성과값으로 사용하지 않았습니다.
